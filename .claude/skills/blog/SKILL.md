# Writing a BreachLine blog post

The blog is part of the Hugo website in `infra/website/src`. Posts are markdown, screenshots come from driving the real app over its MCP server, and the site has built-in responsive + click-to-zoom image handling so you only need plain markdown image syntax.

## Where things live

- Posts: `infra/website/src/content/blog/<slug>.md`
- Images (source): `infra/website/src/content/blog/images/` - blog-local, colocated with the posts, referenced in markdown as `/blog/images/<name>.png`. Hugo copies loose files from the content dir to the same relative path in the output, so `content/blog/images/foo.png` is served at `/blog/images/foo.png`. Do NOT put post screenshots in the theme static dir (`themes/breachline-theme/static/images/`) - that is for site-wide assets like the logo and home page hero only.
- Build output: `infra/website/src/public/` - **gitignored, regenerated by the build**. Never edit it or put source images there; it goes stale.
- App: `application/` (Wails, Go backend + React frontend)

An existing post to copy the shape of: `content/blog/analyzing-cloudtrail-without-decompressing.md`.

## Style rules (from the repo)

- No em-dashes anywhere. Use a spaced hyphen, colon, or reword.
- Do not hard-wrap markdown. One physical line per paragraph or list item; let it wrap.
- Do not number the section headings. Write like a practitioner, not marketing copy.
- Frontmatter:

```
---
title: "..."
date: 2026-01-01T00:00:00Z
draft: false
summary: "One-line teaser shown on the blog index."
---
```

## Screenshots: drive the real app over MCP

The app hosts an MCP server (see `application/doc/MCP_SERVER.md`). Driving it over MCP performs the actions in the visible window, so screenshots are of the genuine app on real data. This replaces any hand-hacking of the frontend.

### 1. Build / locate the app

If `application/build/bin/breachline` is missing or stale, build it. The Wails build tag is `webkit2_41` (NOT `webkit2_42`, which is wrong in some docs):

```
cd application && wails build -tags webkit2_41
```

### 2. Enable the MCP server WITHOUT clobbering the license

Settings live in `breachline.yml` next to the binary (`application/build/bin/breachline.yml`). It usually already holds a `license:` and sync tokens. **Append** the MCP keys, do not overwrite the file:

```
mcp_server_enabled: true
mcp_server_address: 127.0.0.1:8765
mcp_server_token: <any-token-string>
```

Safe append (preserves existing keys):

```
python3 - <<'PY'
import io
p="application/build/bin/breachline.yml"
lines=[l for l in open(p).read().splitlines() if not l.startswith("mcp_server_")]
lines += ["mcp_server_enabled: true","mcp_server_address: 127.0.0.1:8765","mcp_server_token: devtoken"]
open(p,"w").write("\n".join(lines)+"\n")
PY
```

### 3. Launch under the X11 backend (so screenshots work)

The desktop session is Wayland; a native Wayland window is invisible to X11 screenshot tools. Force XWayland:

```
cd application/build/bin
GDK_BACKEND=x11 WEBKIT_DISABLE_DMABUF_RENDERER=1 WEBKIT_DISABLE_COMPOSITING_MODE=1 ./breachline
```

Run it in the background. Wait for the endpoint: `until curl -s -o /dev/null http://127.0.0.1:8765/; do sleep 1; done`. If the binary exits with "will not build without the correct build tags", you built with plain `go build`; use `wails build` instead.

### 4. Drive it

Use the bundled `mcp_drive.py` (stdlib only, no install). Set the token to match `breachline.yml`:

```
export BREACHLINE_MCP_TOKEN=devtoken
python3 .claude/skills/blog/mcp_drive.py help                 # query-language cheatsheet
python3 .claude/skills/blog/mcp_drive.py open-dir /path/to/logs --jpath '$.Records' --pattern '**/*.json.gz' --source
python3 .claude/skills/blog/mcp_drive.py query tab-1 "filter errorCode=* | columns eventTime, eventName, errorCode"
python3 .claude/skills/blog/mcp_drive.py rows  tab-1 --query "filter errorCode=*" --limit 5
```

Key facts about the query language (or run `help`): every stage starts with a keyword, and filters need the `filter` keyword - a bare `errorCode=*` is invalid, `filter errorCode=*` is valid. Operators: `=`, `!=`, `~` (contains), `!~`, `field=*` (present), `field=prefix*`. Stages: `filter`, `columns`, `after`/`before` (times like `24h`, `7d`, or quoted absolute), `dedup`, `limit`. No numeric comparisons.

`open-dir`/`open-file` return the `tabId` to use in later calls. Directory globs are recursive doublestar (`**/*.json.gz`), so point at the top of a partitioned tree.

### 5. Capture the window

Find the window id and grab it with ImageMagick (each `apply_query` updates the grid, histogram, and search bar, so screenshot after the action you want to show):

```
WID=$(DISPLAY=:0 xwininfo -root -tree | grep '"BreachLine"' | grep -oE '0x[0-9a-f]+' | head -1)
DISPLAY=:0 import -window "$WID" shot.png
```

Then Read the PNG to confirm it shows what you expect before using it.

## Resize screenshots (keep them light)

Blog screenshots display at roughly the content width and zoom to ~1200px. Resize to 1200px wide and quantize - dark UI screenshots take 64 colors with no visible loss. Do this into the blog-local images dir (create it if this is the first post with images):

```
mkdir -p infra/website/src/content/blog/images
convert shot.png -resize 1200x -strip -colors 64 -define png:compression-level=9 \
  infra/website/src/content/blog/images/<name>.png
```

Typical result: a full-window shot drops from ~270KB to ~110KB. Read the output once to confirm text is still crisp.

## Embed images so they zoom

Just use standard markdown image syntax with a root-absolute `/blog/images/` path and a real alt caption:

```
![175 failed API calls filtered from the week](/blog/images/cloudtrail-failed-calls.png)
```

You do NOT need any extra markup. The theme already handles it:
- `.post img` CSS (in `themes/breachline-theme/static/css/style.css`) makes images `max-width:100%` so they never overflow on mobile, and frames them like the home page hero.
- `themes/breachline-theme/static/js/post-lightbox.js` (loaded by `layouts/blog/single.html`) makes every post image open enlarged in a modal on click.

So: put the resized PNG in `content/blog/images/`, reference it as `/blog/images/<name>.png`, and it is automatically responsive and click-to-zoom.

## Code blocks

Use plain triple-backtick fences with **no language tag**. A language tag turns on Chroma syntax highlighting, whose inline-styled markup looks inconsistent next to the plain blocks. Keep every code block in a post plain so they render uniformly.

## Build, preview, publish

```
make build-website        # regenerates infra/website/src/public via `hugo --minify`
```

Preview by serving `infra/website/src/public` (e.g. `python3 -m http.server` from that dir) and curl the post + an image to confirm both return 200. If you added images and they 404, `src/public` is stale - rebuild. If using `hugo server`, it may not hot-reload newly added theme static files; restart it.

Commit the post markdown and the images in `content/blog/images/` (both are tracked). `src/public` is gitignored and does not get committed; the deploy rebuilds it fresh. The live site updates on the next `make deploy` / website deploy.

## Cleanup after capturing

- Stop the app (`pkill -f '[.]/breachline'`).
- Restore `breachline.yml`: remove the `mcp_server_*` lines you appended (keep `license` and the sync tokens intact).

## Gotchas (all learned the hard way)

- Build tag is `webkit2_41`. `wails build`, not `go build` (the latter refuses to run without Wails tags).
- Wayland: launch with `GDK_BACKEND=x11 ...` or `import` captures nothing.
- Never overwrite `build/bin/breachline.yml` - it holds the local license. Append.
- Filters need the `filter` keyword; there are no `>`/`<`/`>=`/`<=` operators.
- Post images go in `content/blog/images/` (served at `/blog/images/<name>.png`), not the theme static dir and not `src/public/images/` (that is build output).
- After adding images, rebuild so `src/public` is current before previewing.
